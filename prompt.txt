HAWKABUILD — Final Technical Workflow, AI Models & Team Structure
AppBuildersPH Hackathon · Education · Android-first · Flutter · Fully offline AI · 4 developers
For your team, I recommend an Android-first Flutter application with three local AI components: speech transcription, body-pose analysis, and personalized feedback generation.
The fourth component—document processing—can initially use regular offline algorithms rather than another AI model.
This architecture is designed to avoid paid APIs and cloud subscriptions. I also checked the published versions of the principal libraries and model candidates.

What about speech speed, fillers, and documents?
You don't need to add a model for every feature.
Feature	Recommended implementation
Speaking speed	Word count divided by a clearly defined duration
Filler words	Configurable word/phrase matching over editable transcripts
Long pauses	Audio VAD or validated speech segment timestamps
Body sway	Landmark-based displacement over time
PDF extraction	Offline parser and text quality checks
Missing speech sections	Compare document sections to the transcript
Stars and levels	Deterministic Dart business logic
These methods make your results more explainable than asking a language model to invent scores.

Important implementation notes for this folder structure
- Flutter will generate additional Android, build, Gradle-wrapper and platform files. Keep those generated project files rather than replacing them with only the illustrated tree.
- Drift will generate files such as app_database.g.dart; don't manually edit generated code.
- Model assets are shown with logical filenames. The Qwen filename is a proposed local name, not a verified upstream file name.
- Large AI models should be copied or accessed from assets using a tested storage/loading strategy; don't assume every native runtime can read compressed APK assets directly.
- Do not duplicate model files under both Flutter assets and Android assets. Choose one packaging approach per runtime.
- Add CMake/native library sources only for the engines you actually compile. If using an AAR or Flutter plugin, some native directories may be unnecessary.
- PDF/DOCX parsers must be chosen and license-checked before those services are implemented.
- If your Android project uses Kotlin Gradle scripts, retain .gradle.kts; if Flutter generated Groovy .gradle files, keep that convention instead.

Technical detail: For pose analysis, it is better to collect timestamped landmarks during recording and aggregate them after recording ends. The analyzeSession interface should access that collected data; it should not assume recorded video can magically be analyzed without a video processing pipeline.
Similarly, a speech transcript and raw audio recording are different sources. Word count comes from the transcript, while reliable pause measurement needs audio timing or VAD.

9. Minimum device requirements and realistic limitations
For planning, I suggest testing on a physical Android phone with 6–8 GB RAM or more. This is a development target, not a verified minimum requirement.
The exact requirements depend on the phone's processor, quantization, runtime, recording duration and how many models remain loaded.
Device	Suggested scope
4 GB RAM	Whisper Tiny, MediaPipe Lite, rule-based feedback
6–8 GB RAM	Try Whisper Base, MediaPipe Lite, optional small LLM
12 GB+ RAM	Benchmark richer feedback and potentially larger models
For the first build, process speech and video sequentially where practical. Unload unused AI engines between stages if needed.
One serious technical constraint is the camera: MediaPipe requires suitable frames, while Whisper processes audio. The two should not be forced into a single real-time inference loop without performance testing.
